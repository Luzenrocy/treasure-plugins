## Findings

### R1-002 — P2 — 删除发起后的取消承诺与保持编辑锁要求矛盾

- **位置：** `draft.md` §7.2 第 221–222、234、236 行；§9.3 第 335、338 行。
- **证据：** 第 221 行要求调用删除后保持锁直到结果，但第 222 行将“取消”统一描述为“不删除原文件”并释放编辑锁，第 236 行又承诺“整个离开流程保留取消入口”。本地 SDK `excalidraw/node_modules/treasure-sdk/dist/index.d.ts` 第 141–144 行的 `directories.remove({ directory, name? })` 只返回 Promise/Result，没有取消参数或撤销接口。删除请求已发出时，插件取消等待不能保证宿主不再回收文件。
- **影响：** 若按通用取消规则在 remove 等待期间解锁，用户可继续产生新编辑，而迟到删除结果仍可能移除文件或关闭会话；若始终保持锁，则“整个流程可取消且不删除”的 UI 承诺无法兑现。U-009 的取消及成功/失败反馈仍有歧义。
- **行动：** 将取消保证明确限定到调用 `directories.remove` 之前。删除请求发出后进入不可取消的“正在移到回收站”阶段，保持编辑锁并等待实际结果；成功后更新列表/关闭，失败后保留会话并解锁。删除发起后的取消请求或 token 失效不能被当作已撤回 SDK 操作，也不能虚称原文件未删除。同步调整通用第 5 步、表后文案、删除行和验收场景；其他离开路径仍可在提交前取消。
- **验收：** 方案中分开写明“remove 调用前取消”和“remove 已发出、结果未返回”两种场景：前者不调用删除并恢复编辑；后者没有承诺可撤回的取消入口，锁持续到真实结果，成功/失败分别按宿主返回处理。期间不能因取消提前解锁或将迟到成功误报为取消成功。无需实际实现或执行该测试。
