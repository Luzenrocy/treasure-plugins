# 第 1 轮 / 第 1 次迭代审查

- 审查范围：`draft.md`、`coverage.yaml`、不可变 brief、requirements ledger（version: 1）、adaptive contract、source index、rules snapshot，及 source index 列出的本地来源。
- 审查重点：SDK 2.1.1 的公开类型调用、研发指南与类型声明差异、原型/正式实现边界、相对路径和无依据承诺。
- 覆盖核对：`coverage.yaml` 将 U-001 至 U-009 均标为 `covered`，并声明正式 SDK 基线为 2.1.1；以下发现说明这些覆盖项尚有需要校正的可执行性或可追溯性缺口。
- 合同核对：已按 normative/hybrid contract 的“2.1.1 为正式门槛、文件操作处理 `Result`/`CANCELLED`、不把原型模拟当正式实现、使用本地相对链接”检查。

## Findings

### R01-I01-001 — P1：`saveDialog` 的返回引用与“当前会话”引用被混淆

- **位置：** `draft.md` §3“另存为/导出”行（第 43 行），并影响 §5.2“保存 `.gxp`”（第 86 行）的实现衔接。
- **证据：** SDK 2.1.1 的 `files.saveDialog(options)` 返回 `Result<FileReference>`，即用户在该次系统“另存为”中选择的目标引用；已打开的 `.gxp` 则由 `openDialog` 或目录列举取得已有 `FileReference`，正常保存应直接调用 `writeFile({ file, data })`。S-04 §3.3.2 也明确将 `saveDialog` 返回的当前宿主会话“只写文件引用”直接交给 `writeFile`，且不得持久化。草稿写成“`files.saveDialog` 取得当前会话的 `FileReference`”，倒置了引用来源。
- **影响：** 实现者可能在每次普通保存时重复打开“另存为”，或误以为该 API 能返回已有会话的目标；这会破坏 §5.2 已写明的“有目标直接写、无目标才另存为”流程，也使外部副本与原生正常保存难以正确区分。
- **操作：** 将矩阵拆为“正常保存”和“另存为/导出”：正常保存使用会话内、尚未过期的既有目标引用调用 `writeFile`；无目标的原生首次保存、另存为和每个导出目标，均由 `saveDialog` **返回新的目标 `FileReference`** 后立即 `writeFile`。明确多画布“逐个选择目标”只适用于逐文件导出，不适用于一个 `.gxp` 工作簿的正常保存。
- **验收检查：** 对已打开 `.gxp` 的保存不出现对话框；新建 `.gxp` 首次保存与另存为各出现一次 `saveDialog`，其返回引用立即写入；“全部画布导出”每个输出各一次 `saveDialog`；TypeScript 以 S-06 的 `WriteFileInput` 通过检查，且所有失败/`CANCELLED` 保留原会话。

### R01-I01-002 — P1：`minPlatformVersion` 尚不是可落实、可验证的 SDK 2.1.1 门槛

- **位置：** `draft.md` §3“SDK 2.1.1 正式基线”行（第 40 行）及 §9 发布前检查第 1 项（第 150 行）。
- **证据：** S-06 能证明 `DirectorySetting` 和 `permissions.verifyDirectoryGrant` 的公开类型存在，S-04 要求 manifest 声明最低宿主版本；但所给本地来源没有给出“哪个宿主 semver 首次提供 2.1.1 API 契约”的映射。草稿仅说设为“能提供 2.1.1 契约的宿主版本”，没有值、查证来源或阻断条件。
- **影响：** `package.json` 锁定 SDK 2.1.1 仍可能被低版本宿主加载，目录授权恢复链会在运行时不可用；这不满足 U-002 所要求的可执行设置约束，也无法让 CI/发布审查判定 manifest 是否正确。
- **操作：** 将最低宿主版本标为 `[TBD]`，并新增 P0 阻断项：从实际 2.1.1 宿主发行/manifest 契约取得或联调确认对应的最小版本后，写入精确 `manifest.minPlatformVersion`；若本地资料仍无法提供映射，发布不得声称已完成 2.1.1 兼容，且须在目标宿主上执行 `verifyDirectoryGrant` 的端到端验证。
- **验收检查：** manifest 含一个经来源或目标宿主验证的具体 semver；低于该版本的宿主被拒绝或不进入发布支持范围；目标版本在宿主注册调试中完成 `settings.get → verifyDirectoryGrant → directories.list`。

### R01-I01-003 — P1：快捷键契约遗漏“已有选区”前置条件

- **位置：** `draft.md` §7.2（第 125 行）。
- **证据：** S-01“操作与状态约定”规定：只有“画布获得焦点**且有选区**”时，`Tab` 添加子节点、`Enter` 添加同级节点；草稿只限定了画布获焦且没有文字/中文组合输入，遗漏选区条件。
- **影响：** 无选中节点时的键盘行为变成未定义，实施者可能创建没有父级/同级依据的节点，偏离已调整原型并引入不可预测的无障碍键盘行为。
- **操作：** 在命令契约中加入“有有效节点选区”的必要条件；无选区时明确为不执行结构命令（可保留画布快捷键帮助或状态提示），并把该条件加入键盘回归用例。
- **验收检查：** 在无选区、节点已选、文本编辑、中文 IME 组合四种状态下分别测试 `Tab`/`Enter`；仅“节点已选且不在文本/IME 输入”创建对应节点。

### R01-I01-004 — P2：迭代草稿中的产品证据链接相对层级错误

- **位置：** `draft.md` §1 末句（第 21 行）。
- **证据：** 草稿位于 `council/rounds/round-01/iterations/iteration-01/`，但链接沿用了从 `council/` 出发的 `../../../2026-11-05-native-and-naming/decision.md` 与 `../../../prototype/README.md`。前者会解析到本迭代的 `rounds/2026-11-05-native-and-naming/...`，后者会解析到本迭代的 `rounds/prototype/...`，均不是 S-03/S-01。adaptive contract 要求本地文件相对链接作为证据样式。
- **影响：** 读者无法从草稿直接核验命名和原型口径，削弱 U-001/U-002 的来源可追溯性，并使审查记录中的核心证据成为死链。
- **操作：** 按 `draft.md` 的实际目录重算链接（或以明确、可解析的相对链接替代），并对正文所有本地链接做一次链接解析检查；不要把 source-index 中相对于 `council/` 的路径直接复制到更深层的迭代文件。
- **验收检查：** 从 `iteration-01/draft.md` 打开两条链接，分别到达 S-03 `decision.md` 和 S-01 `prototype/README.md`；链接检查不报告断链。

### R01-I01-005 — P2：外部副本创建后的脏状态与保存修订规则相冲突

- **位置：** `draft.md` §5.2“外部编辑意图”行（第 85 行），与 §4 会话修订规则（第 65 行）及 §5.2“保存 `.gxp`”行（第 86 行）相邻冲突。
- **证据：** 草稿规定副本需编码并通过另存为或已授权目录“创建”，但随后把成功会话固定描述成“可编辑和脏状态”。同一草稿又规定成功保存的快照成为 `savedRevision`，且仅当 `revision !== savedRevision` 才为脏。S-01 仅要求外部文件先复制为新的原生工作文件再编辑，没有要求刚成功写出的副本呈脏状态。
- **影响：** 用户会看到刚创建且已写入的副本仍提示未保存；离开保护可能重复要求保存，也无法用修订号准确判断该副本是否已落盘。
- **操作：** 定义复制事务的状态转换：副本目标选择/写入成功后，新 `.gxp` 为 `editable-clean`，`savedRevision` 等于已写入快照；只有其后的内容编辑才变脏。若目标选择或写入失败，则保持外部只读会话且不得进入可编辑状态。
- **验收检查：** 从 `.smm` 和 `.xmind` 各创建一次副本：成功写入后关闭不提示保存；对副本编辑一次后变脏并触发离开保护；取消或写入失败后原外部预览仍为只读且未被覆盖。

### R01-I01-006 — P2：折叠是内容命令还是非持久视图态尚未作出实现决定

- **位置：** `draft.md` §7.2 命令表“新建/改名/移动/折叠内容”行（第 122 行），以及 §6 的“视图持久化边界”描述（第 93 行）。
- **证据：** 第 122 行同时将“折叠内容”列入更新模型、可撤销、变脏的命令，又附注“视图态折叠除外时需明确”；第 93 行也只说要定义“视图持久化边界”，没有作出决定。S-01 要求折叠即时影响可见分支和缩略大纲，但未替方案选择其持久化/撤销语义。
- **影响：** `SessionStore`、`.gxp` schema、撤销栈和脏状态会按不同解释实现；同一操作可能在保存/重开或撤销时表现不一致。
- **操作：** 在 P0 schema/命令决策中明确一种语义并贯穿 §6、§7 和测试：若折叠是视图态，则不入文档修订/撤销/脏状态，并说明是否随视图保存；若是内容态，则记录到 schema、进入撤销栈和脏状态。将未作决定前的措辞改为 `[TBD]`，避免伪装成已确定契约。
- **验收检查：** 对选定语义运行“折叠 → 保存/重开 → 撤销/重做”的回归；缩略大纲即时反映可见分支，修订与脏状态严格符合已选规则。
